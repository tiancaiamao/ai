# Scoring Rubrics — 会话评价标准

从 Warp skill-doctor (warpdotdev/common-skills) 的四份 scorer rubric 移植改编。
用途:分析 session 时,先按本文件的 rubric 判定,再进入根因分析。**没有 rubric 的分析是即兴发挥,质量不稳定。**

每份 rubric 的结构约定:

- **Labels 表**:每一档有明确分值 + 一句可判定的描述,禁止"较好/一般"这类模糊词
- **Assess 清单**:开头声明"以下是常见来源,不是穷举清单",允许判断清单外的问题
- **Out-of-scope 声明**:明确本维度不评什么,防止维度之间重复扣分
- **Reason 模板**:1-3 句,必须引用具体证据 + 指出可修复的根因

---

## Rubric A: 执行效率 (Efficiency)

评估 agent 到达结果的总成本:步骤、返工、消耗的用户注意力。**基准线是"一个有同样工具的称职工程师需要多少步",不是"agent 碰巧做到的程度"。**

| Label | 描述 | Score |
|-------|------|-------|
| highly_efficient | 直接路径:无重复读/重复跑,独立步骤批量执行,无返工 | 1 |
| mostly_efficient | 偶有失误:一次重复读、一次过早重试,无连锁成本 | 0.8 |
| mostly_inefficient | 反复浪费,或一轮本可预防的返工 | 0.4 |
| highly_inefficient | 浪费主导整场运行:同一缺陷跨周期返工、用户反复纠正、长时间 flailing | 0.2 |

**Assess 清单:**

- **返工**:本地检查本可拦住的测试/构建失败、改错文件、误解需求后回滚
- **用户成本**:用户反复纠正最贵;开工前问一句便宜,造错东西之后才问不便宜
- **信息收集**:重复读/跑/搜已找到的东西;整读大文件而不是定向 grep
- **例行动作开销**:标准步骤走了绕路。⚠️ 权重超出单次运行成本——同样的可避免开销会在每次未来会话中重复,直到有 skill 或规则修掉这个模式。**routine 开销反复出现 = skill 缺失的症状**,这是最重要的归因信号
- **批量缺失**:独立的读/搜索/工作流跨轮次串行执行而不是并行
- **Flailing**:不变策略地重试失败方案;该读代码/文档却靠猜。已放弃的路径只在"避免它的信息当时已可获得"时才计负分
- **验证时机**:检查要早跑一次,在宣布完成前拦住缺陷;完成后补跑或重复跑都算

**Out-of-scope**:产出代码的质量(Rubric C)、是否遵守规则(Rubric B)、话多话少(Rubric D)。

**Reason 模板**:1-3 句,点名主导浪费来源 + 粗略计数("三次修测试循环、四次重复读、两次用户纠正")+ 可修复的根因(缺 skill / 指令含糊 / 检查太晚)。如果存在本应预防该浪费的 skill,点名它。

## Rubric B: 流程合规 (Procedure Compliance)

评估 agent 是否遵守系统上下文中的常设规则,以及是否触发并贯彻了情况所需的 skill。

| Label | 描述 | Score |
|-------|------|-------|
| fully_compliant | 遵守了每条适用规则,触发的 skill 全部贯彻 | 1 |
| mostly_compliant | 遵守了所有重要规则和 skill,只在低风险处有小 slip | 0.8 |
| noncompliant | 漏掉适用规则、跳过已触发的 skill、违反保护性规则、跳过必需验证却报告完成 | 0.2 |

**Assess 清单:**

- **适用性优先于表现**:只判 transcript 显示进入范围的规则和 skill。没触发的规则不奖不罚。**transcript 中完全没有适用规则/skill 时,直接判 fully_compliant**——不因"没规矩"而惩罚
- **机械规则**:分支命名、commit 规范、push 前必需检查。违反即强信号;多部分规则只做了一部分不算满足
- **判断性规则**:注释风格、错误处理惯例——判意图,不抠字眼
- **保护性规则权重最高**:protected branch、force-push、破坏性命令——**违反一次即一票否决**,其他做得再好也没用
- **Skill 未调用**:该触发没触发。更严重的子类:存在就是为了防已知错误的 skill 没触发——通常意味着 skill 的 description 写得不能命中场景
- **Skill 未贯彻**:只做方便的部分;跳过验证/清理步骤却报告完成,是严重失败
- **冲突处理**:规则冲突或规则与指令冲突时,应显式暴露并解决,不许默默挑一个

**Out-of-scope**:任务特定的临时指令;规则/skill 本身设计得好不好(那是本 skill 的分析产出,不是 agent 的错)。

## Rubric C: 产出质量 (Code Quality) — 二元判定

**不打连续分。模拟 senior reviewer 审 PR:会直接 merge 就是 approve;哪怕一个真缺陷会让 reviewer 坚持修掉就是 block。** 二元化的目的是消除连续打分的模糊地带。

| Verdict | 描述 | Score |
|---------|------|-------|
| approve | senior reviewer 会直接 merge,最多 trivial nits | 1 |
| block | 至少一个 reviewer 会坚持修的缺陷:正确性/并发 bug、漏边界、违反惯例、测试弱或缺失、混入不该有的产物 | 0.2 |
| insufficient_evidence | transcript 没展示足够的 diff 来判断 | 排除出统计 |

**Assess 清单:**

- **设计**:变更形状贴合 codebase;无过早抽象、范围蔓延、放错位置
- **正确性**:含边界(nil/空输入)和并发安全
- **复杂度**:无投机泛化、无"为尚不存在的需求"加的间接层
- **仓库惯例**:与同包内相似代码的惯用法一致。**对清晰局部模式的无解释偏离,即使能跑也是缺陷**
- **Smells**:魔法数字、该共享却复制的粘贴、注释掉的代码、含糊 TODO、补症状不治根因的 workaround、被吞掉的错误、该 early-return 却深嵌套
- **测试**:真能验证所声称的行为(坏实现会挂),不是 mock 掉被测逻辑后断言琐碎;覆盖错误路径
- **Diff 卫生**:不留 debug 打印、临时脚本、验证脚手架
- **文档**:README/文档在影响构建/测试/用法时同步更新
- **⚠️ 纠正信号**:用户在会话中指出的缺陷,**即使最终修复了也算 block**——需要外部纠正本身就是负面信号,不只是缺陷未解决

**Out-of-scope**:过程效率(Rubric A)、规则遵守(Rubric B)。只评产物本身。

## Rubric D: 输出克制 (Verbosity)

评估 agent 的自然语言输出是否与工作量相称。**不对称:verbose (0.2) 比 terse (0.1) 罚得轻,但两者都比适中差。**

| Label | 描述 | Score |
|-------|------|-------|
| proportionate | 消息一致地说清"发生了什么、接下来是什么";无重复、无遗漏 | 1 |
| verbose | 反复 padding:复述请求的开场白、预告将做什么、重新描述可见 diff 的总结、填充词代替直述 | 0.2 |
| terse | 沟通不足:长时间沉默、完成时不说改了什么、丢掉收件人需要的信息 | 0.1 |

**Assess 清单:**

- **相称性**:PR description 对照它描述的 diff 判,不对照整场对话
- **Padding**:复述请求、预告动作、给模板要求的 section 写过度 elaborated 的回答(保留必需 section 本身不算 padding,但把它答得很肿算)
- **冗余**:跨消息重复解释同一点;总结的总结
- **膨胀**:"comprehensive / robust" 这类修饰词是填充物的信号
- **沟通不足**:长段沉默;完成消息不说变更和需要 review 的点

**Out-of-scope**:diff 大小、工具输出长度、代码注释量(归 Rubric C)。

---

## 应用方式

1. 选定 session 后,先按四份 rubric 逐个判定并写 Reason(引用具体轮次/内容)
2. **Raw 分 < 0.5 的会话才算"失败会话";只有失败会话能作为改进建议的证据**——防止拿个例泛化
3. `insufficient_evidence` 不算失败,不计入对应维度平均
4. 跨 session 按**根因聚类**(不是按表面问题列清单),按 频率 × 严重度 排序
5. 聚类结果进入改进建议流程——门槛见 SKILL.md「改进建议提案门槛」一节
